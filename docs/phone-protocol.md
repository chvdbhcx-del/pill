# Pill Phone protocol v1

Pill (PC) and the Pill Phone Android app talk over the local network. Both sides are written against this document; change it first, then the code.

## Roles and transport

* **PC (Pill)** runs a small server, only while Settings > Phone > "Phone link" is ON. It binds to the PC's private IPv4 address (never `0.0.0.0` on a public interface), port chosen at first start (default 41717, next free if taken) and remembered. It accepts connections only from private/link-local peers (10/8, 172.16/12, 192.168/16, 169.254/16) and rejects the rest with 403.
* **Phone** is always the client. HTTP/1.1 plus one WebSocket per paired phone. No TLS (LAN only); everything sensitive is protected by the per-device token. The Settings row says so in plain words.
* Content type JSON (UTF-8). Timestamps are Unix milliseconds. Ids are strings.

## Pairing (QR)

1. The Phone tab / Settings shows a QR code for `http://<pc-ip>:<port>/p?c=<code>` where `<code>` is a one-time 8-character code (A-Z2-9, valid 5 minutes, one use).
2. A phone camera opens that URL in the browser. The PC serves a small self-contained page (`GET /p`) with:
   * the PC name, a big **"Download the app"** button -> `https://github.com/chvdbhcx-del/pill-phone/releases/latest/download/PillPhone.apk` (the URL is a constant in Pill, settable by `phone.apkUrl`),
   * a big **"Open in Pill Phone"** button -> `intent://pair?h=<ip>&p=<port>&c=<code>&n=<pc-name>#Intent;scheme=pillphone;package=app.pill.phone;end` (fallback `pillphone://pair?...`),
   * the page is dark, mobile-first, same look as the app (see the app design notes).
3. The app (already installed, opened by that link, or via its own in-app QR scanner) calls `POST /api/pair`:
   ```json
   {"code":"AB3D9XKQ","deviceId":"<uuid generated by the app>","name":"Pixel 8","model":"Pixel 8","os":"Android 15","appVersion":"1.0.0"}
   ```
   -> `200 {"token":"<43-char url-safe random>","pcName":"DESKTOP-X","serverVersion":1}`; wrong/expired code -> `403 {"error":"bad_code"}`. The PC stores only a hash of the token plus the device record (name, model, first/last seen). A second pairing of the same `deviceId` replaces the token.
4. Every later request carries `Authorization: Bearer <token>`; the WebSocket takes `?token=<token>`. Bad token -> 401. The PC lists paired phones in Settings and can revoke each one (the token dies, an open socket is closed with code 4001).

## Realtime channel: `GET /ws?token=...` (WebSocket)

Text frames, one JSON object each: `{"t":"<type>", ...}`. The server sends `{"t":"hello","pcName":"...","serverVersion":1,"time":<ms>}` first. Either side may send `{"t":"ping"}`; the other answers `{"t":"pong"}`. The app pings every 20 s and reconnects with back-off (1 s .. 30 s) after a drop.

### Phone -> PC

* `notif.posted` — a notification on the phone appeared or changed:
  `{"t":"notif.posted","key":"<StatusBarNotification key>","pkg":"org.telegram.messenger","app":"Telegram","title":"Вадим","text":"привет, ...","sub":"","when":<ms>,"category":"msg","ongoing":false,"progress":null,"icon":"<base64 PNG <= 96x96 of the app icon or null>","avatar":"<base64 PNG <= 96x96 of the large icon / sender or null>","canReply":true,"actions":[{"id":"a1","title":"Mark as read"}],"group":"<group key or null>"}`
  (`ongoing` ones such as media players or screen recording are sent but flagged; the PC decides to show them.)
* `notif.removed` — `{"t":"notif.removed","key":"..."}` (dismissed on the phone or by `notif.dismiss`).
* `status` — `{"t":"status","battery":87,"charging":false,"network":"wifi|mobile|none","ssid":"Home"|null,"dnd":false,"time":<ms>}` on connect and when something changes (at most once per 10 s).
* `reply.result` — `{"t":"reply.result","req":"<id from notif.reply>","ok":true|false,"error":"no_action|expired|..."}`.
* `file.offer` — the phone wants to send files: `{"t":"file.offer","id":"<uuid>","name":"photo.jpg","size":123456,"mime":"image/jpeg"}`; the PC answers `file.accept {"id"}` (then the phone uploads over HTTP, below) or `file.reject {"id","reason"}`.
* `file.done` — `{"t":"file.done","id":"...","ok":true}` after the phone finished downloading a PC file.

### PC -> phone

* `notif.dismiss` — `{"t":"notif.dismiss","key":"..."}`: cancel it on the phone (the Hide button).
* `notif.read` — `{"t":"notif.read","key":"..."}`: "mark as read": the app fires the notification's action titled like "Mark as read" if one exists, else cancels the notification.
* `notif.reply` — `{"t":"notif.reply","req":"<id>","key":"...","text":"хорошо"}`: the app fills the notification's RemoteInput action and fires it; answers `reply.result`.
* `file.offer` — PC -> phone: `{"t":"file.offer","id":"<uuid>","name":"Report.docx","size":...,"mime":"..."}`; the phone shows a notification "File from PC" and downloads it automatically when "Auto-receive" is on, else on tap; saves to `Downloads/Pill/`.
* `find` — `{"t":"find"}`: ring the phone (optional, v1.1).

## HTTP endpoints (all with the bearer token except `/p` and `/api/pair`)

| Method + path | Purpose |
|---|---|
| `GET /p?c=` | the download / open page (no token) |
| `POST /api/pair` | pairing (no token) |
| `GET /api/state` | `{"pcName","serverVersion","time","paired":true}`; a cheap connectivity test |
| `PUT /api/up/<fileId>` | phone -> PC upload of an accepted `file.offer`: raw body, `Content-Length` = size; streamed to `Downloads/Pill/` (name sanitised, no path separators, no reserved Windows names, unique suffix on clash); `200 {"ok":true,"path":"..."}` |
| `GET /api/down/<fileId>` | PC -> phone download of an offered file, supports `Range` |
| `DELETE /api/device` | the phone unpairs itself |

Limits: file size cap setting (default 4 GiB), at most 2 transfers at a time, a body larger than announced is cut off, an upload for an unknown/expired id is 404, the whole server returns 429 after 20 bad-token requests per minute from one address.

## PC behaviour the app can rely on

* A notification that arrives while the PC is asleep/off is NOT queued by the PC; on reconnect the app resends the currently active notifications (`notif.posted` for each, flagged `"replay":true`) so the PC can show a quiet digest.
* The PC may ignore apps the user muted (Settings > Phone > Apps); the app keeps sending everything and does not filter.
* `notif.reply` only works for notifications with `canReply:true` (a RemoteInput action exists); the app keeps the `PendingIntent` per key in memory, so a reply after the app process restarted fails with `expired`.

## App design notes (shared look)

Dark by default (follows system light/dark), background `#0B0B0F`, surface glass `#15151C` with 1 px `#FFFFFF14` border, text `#F2F2F7` / `#9A9AA8`, accent = Pill violet `#8E7BFF` with a softer `#B9AEFF` highlight; large radii (24 dp cards, pill-shaped buttons), generous spacing, one typeface (system, weights 500/600/700), spring animations with soft overshoot (the same feel as Pill's liquid motion), a droplet/pill logo mark. Russian + English strings.

## Changes by the PC side

Clarifications and details the PC implements; none breaks the text above (the app should rely on them).

* **One request per connection.** Every HTTP response carries `Connection: close`; open a new TCP connection per request (the WebSocket is the only long-lived one).
* **Silence limit.** The PC drops a WebSocket that sent nothing for 90 s (the 20 s ping keeps it alive). A single message may be at most 1 MiB; client frames must be masked, as RFC 6455 requires.
* **WebSocket close codes.** `4001` = this phone was revoked (stop reconnecting, show "unpaired"); `4000` = a newer socket of the same phone replaced this one (do not reconnect from this one); `1001` = the PC is turning the link off or quitting (reconnect with the usual back-off).
* **`file.offer` from the phone.** The PC answers `file.accept {"id"}`, or `file.reject {"id","reason"}` with reason `too_big` (over the size cap), `bad_id` (the id must match `[A-Za-z0-9_-]{1,64}`) or `declined` (the user said no). When "auto-accept" is off the answer can take as long as the user needs: the app keeps waiting (it may show "waiting for the PC"). The PC sanitises the name; the final name comes back in the `PUT` answer (`path`).
* **Upload errors.** `PUT /api/up/<id>`: `404 {"error":"unknown_file"}` (not announced, not accepted, someone else's id, or already used), `411` without `Content-Length`, `413 {"error":"too_large"}` when `Content-Length` is larger than the announced size, `400 {"error":"size_mismatch"}` when it differs, `503 {"error":"busy"}` with `Retry-After: 2` when two transfers already run (retry), `400 {"error":"interrupted"}` when the body ended early. An accepted offer can be uploaded once; after an error the app sends a new `file.offer` with a new id.
* **Downloads.** `GET /api/down/<id>` answers `200`/`206` with `Accept-Ranges: bytes`, `Content-Range` for `206`, `416` for an impossible range, `404 {"error":"unknown_file"}` for another phone's or unknown id, `503 busy` as above. Send `file.done {"id","ok"}` afterwards. The PC offer id is 32 hex digits.
* **Muted apps and replays.** `notif.posted` of a muted app is dropped without an answer; a `replay:true` notification is listed on the PC but never pops up. A repeat of the same title/text under the same `key` is stored once (progress ticks are cheap).
* **`notif.read` / `notif.dismiss`** remove the notification from the PC list at once; the phone's own `notif.removed` that follows is harmless.
* **`reply.result`** with `ok:true` takes the notification off the PC list; `error` is shown to the user as "expired" / "no_action" / anything else.
* **Pairing page.** `GET /p?c=<code>` also works without a code (only the download button is shown). The deep link carries the PC's LAN address, port, code and name, URL-encoded.
* **Rate limit.** The 20-per-minute counter counts bad bearer tokens and wrong pairing codes together, per source address; while it is over the limit even correct requests from that address get `429`.
* **Binding.** The PC listens on its private LAN address (first free port from 41717 up, remembered); if it has none the link stays off with "no private network".
